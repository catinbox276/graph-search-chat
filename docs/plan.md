> **작성 2026-08-07 · v2.** 초기 기획(2026-08-05)은 [plan-v1.md](plan-v1.md)에 아카이브.
> v1이 "무엇을 만들려는지"였다면, v2는 **PoC 실증을 마치고 사내 전환을 준비하는 시점**의 기획이다 —
> 무엇이 검증됐고, 어떤 기능이 갖춰졌고, 사내에 붙이려면 무엇이 남았는지.

> [integration.md](integration.md)(사내 전환 접점).

## 한 줄 요약

> **직원이 AI 비서(에이전트)와 나눈 "문제 해결 대화"를 회사의 지식 자산으로 바꾸는 시스템.**
> 누군가 한 번 해결한 문제는, 다음 사람이 처음부터 헤매지 않고 그 검증된 길을 안내받는다.
> **핵심 순환(대화 → 야간 자산화 → 경로 제안)은 PoC로 실증 완료** — 지금은 사내 데이터·인프라에
> 그대로 붙일 수 있게 운영 기능을 갖추는 단계다.

        W & F & W2 --> KG["조직 지식그래프"]

v1과 달라진 점은 **②에 문서 경로가 추가**된 것이다. 대화에서만 배우는 게 아니라, 이미 쌓여 있는
사내 문서(블로그·QA·가이드)도 같은 기준으로 판정해 그래프에 넣는다. 그래프에서는 "이 지식이
문서에서 왔는지, 실제 대화에서 왔는지"가 구분되어, 성공/실패 카운트(대화에서만 생김)와 섞이지 않는다.

## 3. 에이전트가 답을 만드는 방식 — 조회 경로 2개

같은 질문 하나에 에이전트는 성격이 다른 두 조회를 쓴다:

1. **지식그래프 경로 제안** — "나랑 같은 문제를 겪은 사람들이 실제로 어떤 경로로 해결했나"를
   먼저 조회한다. 접근법별 성공/실패 횟수, 실패했던 조건의 경고까지 함께 나온다.
   문서 검색으로는 알 수 없는 "검증됐는가"에 답하는 경로다.
2. **사내 문서 하이브리드 검색** — 키워드 검색(한국어 형태소 처리)과 의미 검색(임베딩)을
   융합해 근거 문서를 찾는다. 답변에는 **[1] 각주로 어떤 문서를 참고했는지** 표시되고,
   클릭하면 사내 뷰에서 원문을 확인할 수 있다 (원본 링크 노출은 소스별로 켜고 끌 수 있음).

그리고 사용자는 **에이전트 궤적 타임라인**으로 이 과정을 그대로 본다 — "무엇을 판단했고(🧠),
어떤 도구로 무엇을 확인했고, 그래서 이렇게 답했다"가 단계별로 표시된다. AI 답변의
신뢰는 결과가 아니라 과정의 투명성에서 나온다는 게 이 UI의 취지다.

## 4. 검색 파이프라인 — 등록된 모든 소스 (야간 자동)

원천 테이블을 등록하면 우선 **검색이 되게** 가공된다. 원천이 몇 개든 저장소는
통합 코퍼스 테이블 2개(문서·청크)뿐이라, 소스가 늘어도 구조는 늘지 않는다.

```
03:10 적재    시간 컬럼 기준 신규분만 원천에서 읽어(SELECT만 — 원천에 쓰기 없음)
              역할 매핑으로 검색 문서를 조립해 통합 코퍼스에 저장
              (본문형은 그대로, 질문/답변형은 "질문: … 답변: …"으로 합침)
03:15 청킹    긴 본문을 1,200자 단위(150자 겹침)로 분할
03:30 임베딩  청크를 64건씩 묶어 벡터로 변환 — 어느 모델로 만들었는지 함께 기록해서,
              임베딩 모델을 바꾸면 다음 배치가 자동으로 다시 변환
```

검색 시에는 질문 하나가 **키워드 검색**(Oracle Text — 한국어 형태소 처리)과
**의미 검색**(청크 벡터 유사도)을 동시에 타고, 두 순위를 융합(RRF)해 최종 결과를 만든다.
청크 벡터 전체를 서버 메모리에 올려두므로 검색당 외부 호출은 질문 벡터 변환 1건뿐이고,
임베딩이 아직 없는 문서는 키워드 검색만으로도 잡힌다(무중단 폴백).

## 5. 데이터 구조화 — 대상은 2가지: 문서와 대화

검색과 별개로, 지식그래프에 들어갈 데이터를 구조화한다. **원천이 2종류다**:

| | 문서 (도메인을 지정한 소스) | 대화 (에이전트 세션) |
|---|---|---|
| 입구 판정 | **도메인 적합성** — LLM이 기준 대조, 미달은 제외 | **세션 게이트** — 성공/실패/미완결 판정. 성공만 양의 기여, 실패는 경고 표식, 미완결은 보류 |
| 추출물 | 목표·접근법 (2·3층) | 목표·접근법 (LLM) + 행동/도구 (기록에서 그대로, 4층) |
| 이후 | **클러스터(§5.2) → 저장(§5.3) 공통** | 〃 |

입구만 다르고, 그 뒤(클러스터→저장)는 같은 길을 쓴다. 대화는 판정 전에 **태스크
단위로 분할**부터 한다 — 한 대화에서 문제 A를 풀고 B로 넘어가면, 질문 흐름이 꺾이는
지점(임베딩 유사도 급락)에서 잘라 A·B를 따로 판정·추출한다. 성공·실패가 섞인 세션은
무리해서 정하지 않고 보류(기여 없음)한다. UI도 "다른 문제는 새 대화로"를 안내해
세션=문제 정렬을 돕는다. 그래프에는 출처(문서/대화)가
구분 기록되어 성공/실패 카운트(대화에서만 생김)에 문서가 섞이지 않는다.
도메인을 지정하지 않은 소스는 §4 검색 전용이고 여기로 들어오지 않는다.

### 5.1 문서 구조화 — LLM 판정·추출 (문서 1건 = 요청 1회, 16건 동시)

```mermaid
flowchart TB
    A["원본 문서<br/>(도메인이 지정된 소스)"] --> B["프롬프트 1개로 조립<br/>지시 + 도메인·추출 지침 + 원본 + 출력 서식"]
    B --> C["LLM 응답 = JSON 1개<br/>fits(적합?) · reason(근거) · goal(목표) · approach(접근법)"]
    C -->|"fits=true"| OK["→ 클러스터로 (§5.2)"]
    C -->|"fits=false"| X["제외 기록 (사유와 함께)<br/>그래프에 안 들어감"]
    C -->|"형식 깨짐"| E2["실패 기록<br/>→ 관리 콘솔 '실패 재시도'로 복구"]
```

- **한 번에 처리한다** — "적합한가"와 "추출"을 나눠 묻지 않고 요청 1회로 JSON 하나를
  받는다. 나누면 문서 읽기를 두 번 하는 셈이라 호출(=시간·비용)만 2배가 된다.
- **LLM의 권한은 빈칸 채우기까지** — fits/reason/goal/approach 네 칸이 전부다.
  형식을 어기면 그 문서만 실패로 빠져 재시도된다. 데이터 손실 경로는 없다.
- 16건을 동시에 요청해 두고(설정 가능), 완료된 것부터 다음 단계로 넘긴다 —
  시간당 ~15,000건 (실측).

### 5.2 구조화 클러스터 — 그래프에 넣는 순간마다 병합

"전부 구조화한 뒤 한 번에 묶는" 별도 단계가 아니다. 추출된 문구(목표·접근법)를
**넣는 순간마다 노드 1개 단위로** 기존 그래프와 대조한다 — 그래서 나중 문서가 먼저 온
문서가 만든 노드에 흡수되고, 그래프는 배치 도중에도 항상 정리된 상태다.

```mermaid
flowchart TB
    D["추출된 문구 도착<br/>예: '프록시 환경 pip 설치 실패'"] --> E["임베딩 변환 후<br/>같은 부모 밑 형제 노드와만 비교"]
    E --> F{"얼마나<br/>비슷한가"}
    F -->|"0.92↑ + 문자 검증"| G["✅ 자동 병합<br/>(LLM 안 부름 — 대부분)"]
    F -->|"0.70~0.92 애매"| H["LLM 1회 질의<br/>'후보 중 같은 의도 번호 골라'"]
    H -->|번호| G2["✅ 그 후보에 병합"]
    H -->|"0 (없음)"| I["🆕 신규 노드"]
    F -->|"그 미만"| I
```

- **판정은 16차선, 병합은 1차선** — 그래프를 여럿이 동시에 고치면 "둘 다 '없네? 새로
  만들자'"가 되어 중복이 생기므로 병합은 일부러 한 줄로 세운다. 병합 1건(수십 ms)이
  판정 1건(수백 ms~수 초)보다 훨씬 싸고 통과분(~3할)만 병합 대상이라 병목이 아니다.
- **문자 검증을 함께 거는 이유** — 임베딩 점수 단독 병합은 업계 관행에 없다
  (Graphiti·Neo4j 모두 문자 비교를 AND로 요구). 짧은 문구는 임베딩이 과신하므로
  "둘 다 12자 이상 + 문자열 유사도 통과"를 추가 조건으로 하고, 걸리면 버리지 않고
  LLM 판정으로 넘긴다.
- 삽입 시점에 못 잡은 중복(다른 날 다른 표현으로 들어온 경우)은 **야간 유지보수**가
  2차로 청소한다 — 저빈도 형제 통합, 오래된 잎 흡수, 시간 감쇠.

### 5.3 저장 — 4계층 그래프에, 층과 연결은 코드가 지정

병합/신규가 결정된 노드는 4계층 그래프에 저장된다. 노드는 **반드시 아래 4개 층 중
하나**이고, 연결은 위→아래 방향만 존재한다:

```mermaid
flowchart TB
    D["1층 도메인<br/>예: 사내 노하우"] --> G["2층 목표<br/>예: 프록시 환경 pip 설치 실패"]
    G --> A["3층 접근법<br/>예: pip.conf에 사내 프록시 지정"]
    A --> T["4층 행동(도구)<br/>예: search_docs 검색 → 문서 열람"]
```

**어디에 붙는지는 LLM 소관이 아니다** — "목표는 2층, 접근법은 3층, 부모는 지정된
도메인"이 코드 상수로 박혀 있다. LLM은 '층'이라는 개념 자체를 모른다. 도메인도 LLM
출력이 아니라 소스 등록 때 사람이 지정한 값(대화는 사용 도구 대조로 코드가 결정)이다.
그래서 LLM이 프롬프트를 완전히 무시해도 최악은 "그 문서 제외"까지이며, 그래프 모양이
무너지는 경로는 없다.

층마다 "누가 값을 정하는가"가 다르다 — 설계 결정 1번 "위는 닫고 아래는 연다"의 실체:

| 층 | 값이 고정인가 | 누가 정하나 |
|---|---|---|
| 층의 종류 자체 (4개) | **완전 고정** | 코드 — 5번째 층이나 다른 종류의 노드는 생길 수 없음 |
| 1층 도메인의 값 | **고정 (닫힌 목록)** | 사람 — 관리 콘솔에서만 추가. LLM은 새 도메인을 만들 수 없음 |
| 2층 목표 · 3층 접근법의 값 | **열림 (자동 확장)** | LLM — 문서·대화에서 추출. 병합·추출 지침이 발산을 수렴시킴 |
| 4층 행동(도구)의 값 | 결정적 | 실제 사용된 도구명 그대로 — LLM 창작 없음 |

저장 마무리는 어느 길로 왔든 같다: **연결 사용 횟수 +1, 출처 증거 기록**(어느 문서/
세션에서 왔는지 — 같은 출처가 두 번 와도 중복되지 않음). 그래프 화면 범례의
**"실패 우세"는 5번째 층이 아니라 상태 표시**다 — 실패 횟수가 성공보다 많은 노드에
붙는 빨간 경고 마커일 뿐, 분류 기준이 아니다.

## 6. 관리 콘솔 — 코드 수정 없이 운영하는 장치들

사내 운영의 핵심 요구는 "담당자가 화면에서 관리"다. 전용 관리 페이지(/admin)에 다음이 갖춰졌다:

| 기능 | 하는 일 |
|---|---|
| **계정 관리** | 가입 승인, 관리자 권한 부여/해제, 삭제 — 가입은 자유, 사용은 승인 후 |
| **도메인 시드 관리** | 그래프 1층(분야) 닫힌 목록 관리 — 용도(대화/문서/양쪽)와 추출 지침까지 |
| **원천 테이블 등록** | 사내 DB의 어느 테이블·어느 컬럼을 어떤 역할(제목/본문/질문/답변…)로 구조화할지 등록 — 등록만 하면 야간 적재·검색·전용 검색 도구까지 자동. 접근 가능 테이블은 화이트리스트로 제한 가능 |
| **문서 구조화 운영** | 드라이런(그래프 반영 없이 판정만 미리보기), 실패 재시도, 초기화 재처리(소스/도메인/전체), 처리 진행도 실시간 표시 |
| **전처리 설정** | 배치 건수·동시성·전용 모델 등 — 저장 즉시 다음 배치부터, 재배포 불필요 |
| **모델 레지스트리** | LLM·임베딩·리랭커를 서빙 주소와 함께 등록, 역할별 기본 지정 — 임베딩 모델을 바꾸면 야간 배치가 자동 재임베딩 |
| **도구 서버(MCP) 등록** | 주소만 등록하면 그 서버의 도구들이 에이전트에 자동 조립 — 사내 DataHub 도구 서버(REST 방식) 전용 어댑터 포함 |
| **에이전트 설정** | 시스템 프롬프트 덮어쓰기, 도구별 사용/차단 — 저장 즉시 다음 질문부터 |

품질·안전 장치(세션 게이트, 기준 미달 제외, 출처 추적·롤백, 노출 대비 채택률 보정, 실패 표식
무효화, 시간 감쇠, 닫힌 시드 사람 전용)는 v1 §6 그대로 유지되며 전부 구현되어 있다 — §4~5
파이프라인 각 단계에 이 장치들이 박혀 있다.

## 7. 사용자·보안 — 자체 계정 체계

기획 변경으로 사용자를 앱이 자체 관리한다 (외부 SSO 의존 제거):

- **관리자**: 환경 설정 계정 1개 (분실 시 서버 설정 수정으로 복구 가능)
- **일반 사용자**: 로그인 페이지에서 가입(아이디+비밀번호) → **관리자가 승인해야 사용 가능**
- **권한 2단계**: 일반/관리자 — 관리자는 다른 계정에 관리자 권한을 부여/해제할 수 있다
- **대화 분리**: 대화 세션은 사용자에 묶인다. 목록·이어하기 모두 본인 것만 보인다.
  같은 문제의 "재발" 판정도 사용자 단위라, 남이 같은 문제를 푼 것은 재발이 아니라
  "경로가 유효하다"는 신호로 집계된다.

## 8. 사내 전환 — 맞출 접점은 사실상 1개

외부와 협의가 필요한 접점이 **원천 테이블 하나로 줄었다** ([integration.md](integration.md)):

1. **원천 테이블** — 관리자가 콘솔에서 테이블·컬럼 역할을 등록 (읽기 전용, 원천에 쓰기 없음)
2. ~~인증~~ — 자체 계정이라 협의 불필요
3. ~~DataHub 도구 서버~~ — 사내에 이미 제공 중, 주소 등록만 하면 됨

**사내 DB 준비물** (첫 기동 전 1회, DBA 협조):
- 앱 계정에 Oracle Text(한국어 전문 검색) 권한: `GRANT CTXAPP TO 앱계정;` +
  `GRANT EXECUTE ON CTXSYS.CTX_DDL TO 앱계정;` — 없으면 기동 시 이 안내가 그대로 출력되며 멈춘다
- 그 외 테이블·인덱스는 앱이 기동하면서 스스로 만든다 (일반 개발 계정 권한으로 충분)
