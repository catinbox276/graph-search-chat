# 범용 메모리·탐색 아키텍처 방향성 탐색 (2026-08-20)

외부 탐색 대화(ChatGPT, 사용자 공유)에서 정리된 2026-08 시점 연구 지형 요약과,
우리 시스템(graph-search-chat)과의 대조. 원 대화:
https://chatgpt.com/share/6a86816c-0cac-83e8-a962-0f98745f3826
(주의: 개별 수치·논문 주장은 타 모델 출력으로 이 문서에서 재검증하지 않음 — 방향 참고용)

## 대화의 핵심 결론 (요약)

1. **8원칙**: raw 보존 / source type ≠ semantic type / 1입력→N메모리 /
   구조를 하나로 통일하지 않음 / Event·Case·Procedure·State는 1급 객체 /
   시간은 timestamp가 아니라 validity+history / Vector·Graph·Keyword는 기억이 아니라 view /
   기억은 질문 시점에 재조립(working memory).
2. **라우터 3단**: ① Source Router → ② Genre/Function Router (설명·튜토리얼·문제해결기·실험·후기…)
   → ③ Semantic Role Extraction (problem/attempt/result/procedure/claim/evidence…).
3. **복잡도 통제**: 관점(축)은 무한히 늘 수 있음 → **작은 Core 축(Identity·Semantics·
   Temporal·Provenance·Scope·Epistemic)만 고정**하고 나머지는 도메인별 Plugin Schema.
   Zep 공식 가이드도 custom entity/edge type을 프로젝트당 ≤10으로 제한, 겹치는 타입 정의 금지.
   모든 facet을 ingest 때 미리 계산하지 않음 (항상/조건부/질의시 3단 계산).
4. **"클러스터"는 4개의 다른 문제**: Namespace(격리) / Entity Resolution(동일 실체) /
   Facet·Topic(의미 분류, 다중 소속) / Graph Community(위상 군집, Leiden).
   전부 "클러스터"라 부르면 설계가 섞임. Entity resolution은 2026년에도 미해결
   (Graphiti 실그래프 1.4만 노드에서 동명 노드 4개 생성 이슈, resolution 컨텍스트 O(n) 폭발 이슈).
   핵심 병목은 **candidate generation** (exact+BM25+vector로 후보 수십 개 축소 → LLM resolve).
5. **에이전트 탐색 (retrieval → traversal)**: MRAgent("Memory is Reconstructed, Not Retrieved"),
   MAGMA(같은 메모리에 대한 semantic/temporal/causal/entity 다중 view, policy-guided traversal),
   HAGE(edge 의미도 query-conditioned, RL 최적화), A-RAG(keyword/semantic/chunk-read 계층 도구),
   AgenticRAGTracer(실패 2형: premature collapse / over-extension — 종료 판단이 어려움).
   에이전트에게 자유 Cypher가 아니라 **제한된 메모리 API**(search_semantic/search_case/
   follow_relation/get_neighbors/get_timeline/get_source…)를 주고 탐색 예산(step/hop/token)을 둠.
6. **가장 중요한 역설**: 에이전트가 탐색할 수 있으면 **완벽한 그래프를 미리 만들 필요가 줄어듦** —
   "저장은 단순하게, 탐색은 똑똑하게". 완전한 온톨로지 사전 구축 문제가
   "탐색 가능한 memory space" 문제로 바뀜.
7. ingestion 13단계: raw → scope → semantic routing → entity 추출 → candidate search →
   resolution → canonicalize → relation 추출 → temporal/conflict(supersedes·corrects·
   contradicts·refines·confirms 구분) → graph attach → facet → local community update →
   주기적 consolidation.

## 우리 시스템과의 대조

이미 일치 (구현됨):
- raw 보존·derived=view: 원천 읽기전용 + corpus_docs 진실, nodes/entity_relations는 ref 역추적,
  초기화→재구조화 지원. 검색 인덱스도 파생물(SQLite :memory:).
- 제한된 메모리 API로서의 에이전트 도구: suggest_paths / search_docs / read_doc / search_{소스}.
- candidate generation → resolver 패턴: merge.py dedup이 정확히 이 구조
  (임베딩 후보 수집 → 문자 가드 → llm_select 후보선택).
- 주기적 consolidation: graph_maintenance (형제 통합·잎 흡수·시간 감쇠).
- Case/Procedure 1급 객체: 4계층 그래프 자체 (목표→접근법→행동, 성공/실패 카운트, 실패 경고).
- corrects의 초기형: 재발 소급 취소(retracted). supersession 슬롯: nodes.valid_from/valid_to.
- 스키마 = 작은 코어 + 커스텀: 엔티티 라인(역할 3종 + 속성 + 관계, 전부 버전).

격차 (우선순위 순):
1. **추출한 관계를 에이전트가 안 씀** — entity_relations는 현재 그래프 뷰 시각화 전용.
   get_neighbors/follow_relation류 도구를 에이전트에 주면 "저장은 단순하게, 탐색은 똑똑하게"의
   탐색 절반이 생김. 비용 낮고 가치 높음.
2. **장르 라우터 없음** — 라우팅 단위가 소스(도메인) 1:1. 한 소스 안 혼합 장르(설명·해결기·
   튜토리얼)를 문서 단위로 맞는 엔티티 라인에 라우팅해야 확장됨. (run에 라인 후보 다중 지정 +
   분류 단계 — 별도 플랜)
3. 용어: 우리 "② 병합(클러스터)"는 실체가 Entity Resolution 설정 — 대화의 지적대로
   community와 혼동 여지. 개명 후보.
4. conflict 유형 구분(supersedes/corrects/…), event_time/observed_at 분리 — bi-temporal 후속과 함께.

의도적으로 안 하는 것 (PoC 규모 30건~수천 건 문서에 과함):
- Leiden community 층, RL traversal policy, frontier/탐색예산 상태기계 (DeepAgents 루프가 저비용 대체),
- 모든 관점의 사전 materialize (대화 자체가 "하지 말라"고 결론).
