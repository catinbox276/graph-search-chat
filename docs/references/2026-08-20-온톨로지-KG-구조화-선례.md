# 온톨로지·엔티티 기반 KG 구조화 프로젝트 조사 — 베이스 선정

> 2026-08-20. 목적: "온톨로지·엔티티로 구조화하는 프로젝트를 기반으로" 전환 — 후보 조사
> 및 우리 제약(Oracle 19c 단독 저장·온프레미스 vLLM·structured output 불가·한국어) 대조.

## 결론 먼저

**통째로 임베드할 수 있는 후보는 없다.** Oracle 단독 + 제약 디코딩 불가 조합이
Graphiti(Cypher 그래프 DB 필수)·Neo4j Builder·Cognee·TrustGraph를 저장 계층에서 자른다.
따라서 "기반으로 삼는다" = **데이터 모델·프롬프트·파이프라인의 포팅**이며, 순위는:

| 순위 | 프로젝트 | 채택 방식 |
|---|---|---|
| **1** | **Graphiti** (getzep, ★30k, Apache-2.0) | **온톨로지 모델 포팅** — Pydantic 엔티티/엣지 타입 + `edge_type_map`(엔티티쌍→허용 관계), 추출→후보검색→LLM dedupe→엣지 타입분류 파이프라인, 프롬프트 한국어화. 저장은 우리 Oracle 테이블 + 인메모리 인덱스로 재구현 |
| 2 | LlamaIndex PropertyGraphIndex | 유일한 임베드 경로 — `DynamicLLMPathExtractor`(프롬프트 기반) + Oracle-backed 스토어 자작. 대가: 프레임워크 종속 |
| 3 | OntoGPT/SPIRES (LinkML) | 방법론 차용 — 스키마→프롬프트 자동 생성 + structured output 없는 재귀 추출(우리 게이트웨이 제약에 가장 안전한 교과서) |

## 현재 자산과의 관계

우리는 이미 Graphiti "커스텀 엔티티 타입"의 절반을 보유: 관리자 정의 추출 스키마
(역할 entry/solution/attr, 버전 관리) + layer-5 엔티티 노드 + 정확일치 병합.
**부족한 것 = 관계(relation) 스키마와 관계 추출·해소.**

## 실행 제안 (기존 자산 유지, 최단 경로)

1. **관계 스키마** — Graphiti `edge_type_map` 개념을 관리자 콘솔에: 관계 타입(이름·설명)
   + 허용 엔티티쌍(출발 타입→도착 타입) + 속성. 엔티티 스키마(버전)와 함께 버전 관리.
2. **추출** — Graphiti `graphiti_core/prompts/` 포팅(한국어화) 또는 LLMGraphTransformer
   패턴: 스키마의 타입·관계 목록을 프롬프트에 주입, JSON 파싱(+재시도) — SO 불필요.
3. **해소(dedup)** — ATOM 임계값 코사인(엔티티 0.8/관계 0.7) + Graphiti식 LLM 판정
   하이브리드 = 우리 기존 2단계(임계값+llm_select) 병합과 동일 철학, 관계로 확장.
4. **저장** — Oracle 신규 컬럼/테이블(edges에 relation_type 등) + 기동 시 인메모리
   그래프 재구축(기존 inmemory_index 패턴). 별도 그래프 DB 없음 — design §6 유지.
