# PoC 결과: 그래프 파이프라인 실증 (2026-08-01)

> 실행 환경: DeepAgents + qwen3.6-35b-a3b(로컬) / DataHub 공식 MCP + Oracle 블로그 검색 함수 / self-play 47세션 → 그래프 파이프라인 v2

## 결론 먼저

**설계의 전체 순환이 처음으로 실증됐다**: 대화 세션 → 게이트 판정 → 4계층 추출 → dedup 병합 → 가중치 누적 → 실패 표식까지 전 단계가 동작.
핵심 증거: **R1(같은 의도를 4가지 표현으로) 4세션이 목표 노드 1개 + 접근법 노드 1개로 정확히 병합**되어 가중치가 쌓였다.

## 수치 요약 (v2 기준)

| 항목 | v1 (임계값 0.85) | v2 (임계값 0.72) |
|---|---|---|
| 게이트 판정 | success 25 / fail 22 | success 34 / fail 12 / unknown 1 |
| 2층(목표) 노드 | 43 (병합 거의 없음) | 27 |
| 3층(접근법) 노드 | 47 (병합 0건) | 33 |
| R1 4세션의 병합 | 목표 3개·접근법 4개로 분산 | **목표 1개·접근법 1개** ✅ |
| 최고 가중치 경로 | 전부 1 | **7** (financial 계좌 조인 경로) |

상위 경로 예: `[7] financial DB 계좌 테이블 및 조인 키 확인 → 데이터셋 검색 후 엔티티 스키마 조회로 조인 키 도출`, `[3] orders 상류 리니지 → get_lineage 추적`, `[3] 프록시 pip 문제 → search_blog + pip.conf`

실패 표식: F1~F5(의도된 실패 태스크) 전부에 fail_flag + 이유가 정확히 기록됨 — 예: "sqlite 플랫폼은 리니지 정보를 지원하지 않아 상류 소스 조회 불가"(F2), "직원 급여 테이블이 존재하지 않음"(F4).

## v1 → v2에서 고친 것 (검증으로 발견)

1. **dedup 임계값 캘리브레이션** — 실측: 이 임베딩 모델(qwen3-embedding-0.6b)에서 **같은 의도 쌍 = 코사인 0.81~0.83, 다른 의도 쌍 = 0.34~0.46**. 0.85는 같은 의도조차 병합 못 함 → 갭 중간인 0.72로 조정. *교훈: 임계값은 임베딩 모델별로 반드시 실측 캘리브레이션.*
2. **게이트 규칙 분리** — v1은 "해법은 맞는데 인용 형식 미달"까지 fail로 판정해 실패 표식이 22개로 오염. v2는 fail을 "접근 자체가 막힌 경우(데이터/글 부재)"로 한정, 품질 미달은 unknown 처리.

## 남은 이슈 (다음 반복에서 다룰 것)

1. **인접 의도 과병합** — 가중치 7 노드의 출처를 검사한 결과 R1×4 외에 R2(대출 분석)×2, S1(district 스키마)×1이 흡수됨. "financial DB 관련"이라는 공통성 때문에 0.72에서 붙음. 개선안: 임계값 0.75~0.78 재탐색, 또는 2단계 판정(임베딩 후보 → LLM에 "같은 접근법인가" 확인). 연구 조사에서 경고한 "dedup 정확도가 가중치의 의미를 결정" 그대로.
2. **fail_flag가 불리언이라 인기 노드 오염** — 성공 7회 쌓인 노드에 실패 세션 1건이 fail_flag를 붙일 수 있음. 설계(bi-temporal supersession) 취지대로 **성공/실패 카운트로 전환**하고, 실패 우세일 때만 경고 노출해야 함.
3. **한국어 질의 ↔ 영어 코퍼스 미스매치** — 블로그 태스크 실패 일부는 한국어 검색어가 영어 문서에 안 걸린 것. 에이전트가 스스로 영어로 재질의한 세션은 성공. 시스템 프롬프트에 영어 재질의 힌트 추가 또는 질의 번역 단계 검토.
4. **판정 LLM 편차** — 같은 기준으로도 세션별 판정이 갈리는 경계 사례 존재(R6-3, R8-1 등). expect 문구를 판정 친화적으로 다듬거나 2-vote 판정 검토.

## 재현 방법

```bash
.venv/bin/python graph/selfplay.py          # 47세션 실행 (이어하기 지원)
.venv/bin/python graph/graph_pipeline.py    # 게이트 + 추출 + 그래프 적재
# 결과는 Oracle: sessions(verdict), nodes/edges(가중치), node_evidence(출처)
```

## 추가: 하이브리드 검색 전환 완료 (2026-08-02)

이슈 3(한국어 질의 ↔ 영어 코퍼스 미스매치)을 하이브리드 검색으로 해소했다.

- **구조**: 임베딩 원본은 Oracle `blog_posts.embedding` BLOB에 저장(1회성 백필, 병렬 4요청으로 34.3만 건 약 4시간), 검색 서버 기동 시 numpy 행렬(1.4GB)로 메모리 로드. 검색 = Oracle Text(lexical) top-30 + 행렬 코사인(semantic) top-30 → RRF 융합. 검색당 임베딩 계산은 질의 1건뿐.
- **검증**: 한국어 질의 "사내망 프록시 때문에 파이썬 패키지 설치가 안 됨" → 영어 글 "Failed to parse: proxy:port"(pip 프록시 오류) 시맨틱 매칭 ✅ / 영어 질의는 L+S 동시 매칭 ✅ / 채팅 E2E에서 search_blog×3 + read_blog_post×3 → 근거 기반 답변 ✅
- **운영 노트**: 새 글은 해당 글만 임베딩 후 `GET /reload` (전체 재계산 없음). 임베딩 모델 교체 시에만 전체 재백필 + dedup 임계값 재캘리브레이션 필요.
- **남은 노이즈**: 한국어 질의 시 lexical 쪽이 지식인 생활 Q&A를 끌어옴 — 코퍼스 품질 문제(실제 사내 블로그로 교체 시 소멸), 검색 로직 튜닝 대상 아님.

## 추가: 그래프 기반 방향 제안 완성 (2026-08-02) — 설계 순환 완결

설계 ⑤단계(신규 사용자 안내)를 구현해 **대화 → 추출 → 병합 → 가중치 → 안내 → 새 경험 재축적**의 전체 순환이 완결됐다.

### 구현 (search/path_suggest.py)
- 에이전트가 새 문제를 받으면 **suggest_paths를 가장 먼저 호출**하도록 시스템 프롬프트 지시
- 동작: 문제 문장 임베딩 → 2층(목표) 노드와 브루트포스 코사인 (진입 임계값 0.60 — dedup 0.72보다 완화) → 유사 목표의 3층(접근법)을 엣지 가중치 내림차순 제시 + 4층 도구 목록 동반
- **성공/실패를 세션 판정 카운트로 집계** — `node_evidence × sessions.verdict` 조인. poc-results 이슈 2(불리언 fail_flag 오염)의 해법을 적용한 것. 실패 우세일 때만 경고, 하드 차단 없음(design §4)
- 노출 기록: 제안된 노드를 `suggestions` 테이블에 저장 → 추후 "노출 대비 채택률" 가중치 보정(이슈 1의 피드백 루프 대책)의 데이터 기반

### E2E 검증
| 시나리오 | 결과 |
|---|---|
| "고객 계좌 데이터 분석 어디서부터?" (R1 유사) | 툴 순서 suggest_paths → search → get_entities…, 답변에 **"과거 조직에서 6회 검증된 방법"** 인용 ✅ |
| "사내 VPN 신청 어떻게 해?" (F3 유사) | **"과거에도 시도했으나 코퍼스에 없어 확인 못 한 이력"** 을 먼저 고지 후 일반 안내로 전환, 차단 없음 ✅ |

### 발견: 이슈 2가 제안 품질에 실제 영향
suggest_paths 첫 버전에서 성공 6회 경로가 실패 1건의 fail_flag 때문에 "과거 실패한 접근(7회 시도)"으로 표시되는 문제가 실제 발생 → 카운트 집계로 전환해 "✅ 성공 6회, 실패 1회 있음"으로 해소. **불리언 실패 표식은 인기 노드에서 반드시 오염된다**는 것이 실증됨 — 사내 적용 시에도 카운트 방식 필수.

### 남은 것 (설계 대비)
- 노출 대비 채택률 가중치 보정 배치 (suggestions 데이터가 쌓인 뒤)
- bi-temporal supersession 자동화 (재시도 성공 시 실패 카운트 리셋이 아닌 시점 기록)
- 유도 통행 vs 자발 통행 구분 (제안을 보고 따라갔는지 기록)

## 추가: 스트리밍 중 마크다운 실시간 렌더 (2026-08-02)

기존에는 토큰 스트리밍 구간을 생 텍스트로 표시하고 완료 시점에만 마크다운을 적용해, 답변이 끝나는 순간 화면이 확 바뀌는 점프가 있었다. 누적 버퍼를 스트리밍 중에도 계속 마크다운으로 재렌더하는 방식으로 전환(ChatGPT류 표준 방식).

- **100ms 스로틀**: 토큰마다 재파싱하지 않고 0.1초당 1회만 렌더 — 체감 실시간 유지하면서 CPU 낭비 방지
- **미완성 코드블록 보정**: 열린 채 스트리밍 중인 코드펜스(``` 홀수 개)는 임시로 닫고 파싱 — 코드블록이 열리는 순간 이후 텍스트 전체가 코드로 보이는 깨짐 방지
- **검증**: 스트리밍 진행 중 스크린샷에서 헤더·표·코드블록이 완성형으로 자라나는 것 확인 (전송 버튼 비활성 상태에서 표가 렌더된 화면)
- **운영 노트**: 앱이 파드 이미지로 서빙되므로 UI 수정은 `docker build` + `kubectl rollout restart` 필요 (~1-2분). 잦은 UI 반복 개발은 호스트 uvicorn으로 하고 파드는 배포 확인용 권장

## 추가: 노출 대비 채택률 보정 가중치 (2026-08-02) — 피드백 루프 대책 완성

research.md가 최대 구조적 위험으로 꼽은 "인기 가중 피드백 루프"(많이 보여줘서 많이 간 길이 좋은 길로 굳는 왜곡)의 대책을 구현. 마지막 남았던 핵심 설계 과제.

### 메커니즘 (3단계, 전부 자동)
1. **노출 기록**: 서버가 세션 id를 contextvar로 도구까지 전파 → suggest_paths가 제안한 노드를 `suggestions(session_id, node_id)`에 기록
2. **채택 판정**: 야간 파이프라인이 세션 판정 시 "제안받은 노드를 실제 사용했는가"를 결정적으로 판정(`node_evidence` 존재 여부) → adopted Y/N
3. **가중치 보정**: `weight = 자발 통행 + 채택 통행 × 채택률(채택/노출)` — 제안 노출로 생긴 통행을 채택률만큼 할인. suggest_paths는 원시 빈도가 아닌 **보정 가중치 순**으로 제안

### 검증 (실측)
| 케이스 | 결과 |
|---|---|
| 노출→세션 연결 | 채팅 1회에 노출 4건이 session_id와 함께 기록 ✅ |
| 채택 판정 | 실제 사용한 경로만 Y, 나머지 3건 N ✅ |
| 공식 검증 | 통행5·노출1·채택1 → 보정 5 (채택률 100% = 무할인), 통행2·노출1·채택0 → 보정 2 (미채택 노출은 통행 미포함 = 무할인) — 산식 정확 ✅ |

노출 데이터가 적은 초기에는 보정이 미미하고, 운영에서 "많이 노출되지만 채택 안 되는" 경로가 생기는 순간부터 할인이 가시화된다. 남은 후속: 탐색 예산(ε-greedy 비인기 노출), supersession 자동화, 사내 전환 시 비식별화.
